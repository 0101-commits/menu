## 0. 결론

맛핀은 기능이 부족한 초기 제품이 아니다. 4,084개 즐겨찾기, 네이버·카카오·구글 평점 비교, 지명/가게 검색, 반경·지도·전체 범위, 필터·정렬, 지도-목록 연결, 모바일 3단 시트, 상세·방문기록, 주변 발견, URL 복원, PWA, Worker/KV와 데이터 CI까지 이미 있다.

다음 개편의 권고 방향은 **새 기능을 넓게 추가하는 것보다 현재 기능을 잃지 않게 만들고, 사용자가 막히는 지점을 회복 가능하게 만드는 것**이다.

1. **P0 회귀 방지:** React/effect/상호작용 테스트를 먼저 만든다.
2. **P1 체감 개선:** 방문기록 백업·복원, 검색/필터 0건 회복, 접근성을 개선한다.
3. **P2 제한적 구조 개선:** 테스트가 생긴 뒤 `App.tsx`와 `MapView.tsx`를 테스트 가능한 경계까지만 나눈다.
4. **P3 실사용 검증 후 선택:** 클러스터·hover·번호 마커 안정화와 성능 개선은 측정 결과가 있을 때만 한다.

**권고 구현안은 P0 전체 + P1 전체 + P2의 최소안이다.** 예상 규모는 4~6 작업일이다. P2 확장과 P3는 이번 승인 범위에서 제외한다.

## 2. 요청 이력에서 확인한 사용자의 기준

대화 원문과 실제 승인 흐름에서 다음 성격이 반복됐다.

### 2.1 “실제 사용자가 느끼는가”가 우선

- 지도에서 선택한 가게가 목록 최상단에 없거나 팝업이 목록 뒤에 숨는 문제처럼, 기능 존재 여부보다 **실사용 흐름의 마찰**을 지적했다.
- 모바일에서 카드가 보이는 수, 새로고침으로 위치를 잃는 문제 등 **체감 가능한 개선**을 요구했다.
- 기획도 네이버·카카오·구글 지도의 화면 전환과 UI를 조사한 뒤 작성하도록 요청했다.

기획 원칙: 내부 구조 개선만으로 끝나는 회차를 만들지 않는다. 각 단계에 사용자가 직접 확인할 결과가 있어야 한다.

### 2.2 숫자는 많음보다 신뢰가 우선

- “카카오 평점이 있는데 표기 안 된 곳이 많다. 다시 한 번 전수검사”, “그럼 구글도 같이 봐야 하는 것 아니냐”는 요청이 반복됐다.
- 구글 값은 초기 전량 시드, 장기 보관, 이후 부분 갱신을 원했다.
- 기존 구현도 오매칭 게이트, 축소 방지 게이트, `수집 전/미매칭/별점 없음` 구분으로 이어졌다.

기획 원칙: **틀린 값은 빈 값보다 나쁘다.** 부재, 실패, 미수집, 미매칭을 하나의 `—`로 숨기지 않는다.

### 2.3 완료 상태와 실제 진행률을 분명히 요구

“끝났어?”, “몇 퍼센트 남았는지”, “현재까지 진행률 보고”, “오류나 이슈 없는지 모니터링” 요청이 여러 세션에서 반복됐다.

실행 원칙: 구현 승인 후에는 단계별로 `완료 수/전체 수`, 검증 결과, 남은 차단 요인을 보고한다. 장시간 수집이나 CI를 “진행 중”으로 뭉뚱그리지 않는다.

### 2.4 기획과 구현을 분리해 결정

처음에는 기획을 요구하고, 검토 뒤 “해당 기획안대로 작업 진행”, “우선순위 순으로 작업 시작”으로 구현을 승인했다.

실행 원칙: 이 문서는 구현 승인용이다. 승인 전 제품 코드는 건드리지 않으며, 승인 시 선택된 범위만 구현한다.

## 4. 현재 남은 문제

### G1. 상호작용 회귀를 배포 전에 잡지 못한다

과거 회귀는 지도 없음→목록 0곳, ratings 도착→지도 리셋, URL 상태 미반영, 무한 스크롤 정지, 상세 뒤로가기 이탈처럼 대부분 effect와 상태 결합에서 발생했다. 현재 selftest로는 이 경로를 실행할 수 없다.

### G2. 방문기록 내보내기가 구현됐지만 사용자가 쓸 수 없다

`src/lib/visits.ts`의 `exportJson()`은 완성돼 있으나 `App.tsx`는 `visits/toggle/setNote`만 사용하고 내보내기 UI가 없다. 가져오기는 구현되지 않았다. 브라우저 데이터를 지우거나 기기를 바꾸면 메모와 방문 표시를 잃는다.

### G3. 검색 실패 후 회복 동작이 약하다

`runSearch()`는 지명과 가게 이름을 정교하게 구분하고 위치를 못 찾으면 가게 이름 검색으로 대체한다. 하지만 최종 목록이 0건일 때 **반경이 좁은지, 필터가 과한지, 지도 범위 밖인지**를 구분해 바로 복구할 방법이 없다. 현재는 안내 문자열 중심이다.

### G4. 코드가 동작 이유를 설명하지만 수정 경계가 너무 크다

`App.tsx` 831 LOC 한 함수에 데이터 로딩, Google 합류, 검색, 발견, 필터, 정렬, URL, 지도 상태, 상세가 함께 있다. `MapView.tsx` 746 LOC에는 명령형 Kakao SDK와 React effect가 섞여 있다. 좋은 “왜” 주석은 많지만 한 변경의 영향 범위를 좁히기 어렵다.

### G5. 운영 문서와 실제 동작이 어긋난다

- README는 구글 값을 매일 03:30 KST Cron Trigger로 갱신한다고 쓰지만 `worker/wrangler.toml`의 `[triggers]`와 `crons`는 주석 처리돼 있다. 실제는 “본 순간 갱신”이다.
- `src/lib/worker.ts` 머리말에는 구글 값을 30일 캐시한다고 남아 있어, 현재 “영구 시드+부분 갱신” 결정과 다르다.
- Worker 배포는 수동이다. 과거 코드와 배포본이 달라 구글 칸이 안 뜬 전례가 있다.
- GitHub 이슈 #4의 즐겨찾기 동기화 실패가 열려 있다. 안내상 가장 흔한 원인은 `NAVER_COOKIE` 만료다.

## P0 — 회귀 방지와 운영 진실 정리

### P0-1. 프런트 테스트 기반 추가

**사용자 가치:** 이미 고친 지도·목록·뒤로가기·모바일 동작이 다음 변경에서 다시 깨지는 일을 줄인다.  
**최소 구현:** 현재 selftest는 유지하고 Vitest 기반 테스트 명령을 추가한다. React 렌더가 필요 없는 필터/정렬 계산을 `src/lib/place-query.ts` 같은 순수 모듈로 먼저 추출한다.  
**우선 케이스:**

1. 지도 데이터가 아직 없거나 실패해도 전체 장소가 0건으로 사라지지 않는다.
2. 평점 데이터가 늦게 도착해도 영업중/최소평점 필터가 전량 탈락시키지 않는다.
3. 같은 사용자 조건에서는 지도 이동 뒤 목록 `resetKey`가 유지된다.
4. 거리·평점·리뷰 정렬과 상위 20 번호 순서가 일치한다.
5. 지명 검색, 가게 검색, 카테고리 토큰 결합이 기존 결과를 유지한다.

**수용 기준:** 기존 selftest 전부 + 신규 순수 테스트 10건 이상 통과. `npm test` 한 번으로 모두 실행.

### P0-2. 핵심 React 상호작용 회귀 테스트

**최소 구현:** 실제 Kakao SDK는 목으로 격리하고 아래 사용자 흐름만 검사한다.

- 카드 선택→상세 열기→브라우저 뒤로가기→목록 복귀.
- 모바일 마커 선택→“지도에서 고른 곳” 고정 카드 표시.
- URL로 `place`, `c`, `z`, 필터를 열었을 때 상태 복원.
- places 준비→ratings 지연 도착의 로딩 상태 전이.
- 검색/필터 조건을 바꿀 때만 목록이 위로 리셋.

**수용 기준:** 과거 회귀 5종을 재현하는 테스트가 있고 CI에서 실패 시 배포되지 않는다.

### P0-3. 운영 문서·주석을 실제 동작과 일치

**최소 구현:** README의 크론 설명을 “본 순간 갱신”으로 정정하고, 예약 크론은 현재 비활성임을 분명히 한다. `src/lib/worker.ts`의 오래된 30일 설명도 현재 정책으로 고친다. #4 동기화 실패의 점검 절차와 마지막 성공 여부를 운영 체크리스트에 둔다.

**수용 기준:** README, wrangler 설정, Worker 코드, 프런트 주석이 같은 갱신 방식을 설명한다. `grep`으로 활성 크론이라고 잘못 서술한 문장이 남지 않는다.

## P1 — 사용자가 바로 느끼는 개선

### P1-1. 방문기록 백업·복원

**최소안:** 설정/내 기록 영역에 `방문기록 내보내기`를 연결한다.  
**권고안:** 가져오기까지 추가한다. JSON 스키마를 검증하고 기본 동작은 **기존 기록과 병합**, 충돌 시 `at`이 최신인 기록을 사용한다. 덮어쓰기는 별도 확인이 있을 때만 허용한다.  
**오류 원칙:** 잘못된 파일, 알 수 없는 place ID, 저장소 차단을 조용히 성공으로 표시하지 않는다.

**수용 기준:** 내보내기→브라우저 데이터 초기화→가져오기 후 방문 수·시각·메모가 동일하다. 잘못된 파일은 기존 기록을 훼손하지 않는다.

### P1-2. 0건 검색/필터 회복 UI

목록 0건을 다음 원인으로 나눠 안내한다.

| 원인 | 제안 동작 |
|---|---|
| 반경 안에 없음 | `반경 넓히기` |
| 선택 필터로 모두 제외 | `필터 초기화` 또는 제외한 조건 표시 |
| 현재 지도 범위에 없음 | `전체에서 보기` |
| 위치 해석 실패 | 현재처럼 가게 이름 검색으로 전환 + `다른 위치로 검색` |
| 데이터 로딩/지도 실패 | “결과 없음”이 아니라 실패 상태와 재시도 |

버튼은 상태와 URL을 함께 바꿔 새로고침·공유·뒤로가기 결과가 일치해야 한다.

**수용 기준:** 위 5상태가 서로 다른 문구와 다음 행동을 제공한다. 버튼 1회로 결과가 있거나 범위가 명시적으로 넓어진다. 결과 수 변화는 `aria-live`로 전달한다.

### P1-3. 가독성·접근성 잔여 종결

- 선택 카드 닫기, 번호 마커, 시트 핸들의 44×44px 터치 영역 실측.
- 키보드만으로 검색→필터→목록→상세→닫기 이동 가능.
- 선택 상태를 색만으로 구분하지 않기.
- 라이트/다크에서 텍스트와 상태 색 대비 자동/수동 점검.
- 검색 결과 수, 오류, 로딩 완료를 적절한 live region으로 안내.

**수용 기준:** 모바일 390×844와 데스크톱 1440×900에서 확대 200%까지 주요 조작이 잘리지 않는다. 키보드 포커스가 보이고 상세를 닫은 뒤 원래 카드로 돌아간다.

### P1-4. 데이터 신뢰 상태를 한 곳에서 확인

현재 여러 문서와 콘솔에 흩어진 정보 중 사용자에게 필요한 최소 정보만 `데이터 정보`에 제공한다.

- 즐겨찾기 장소 수와 마지막 동기화 기준일.
- 네이버·카카오·구글 매칭/평점 보유 비율.
- 구글 값의 개별 수집 시각은 기존 `at`을 유지.
- Worker 연결 실패와 평점 없음은 구분.

이 기능을 위해 개인 키, 원시 응답, 비용 정보는 화면에 노출하지 않는다. `places.json`/`ratings.json`에 생성 메타데이터가 없으므로, 구현 시 데이터 파일 스키마를 깨지 않는 별도 `meta.json` 또는 빌드 메타 필드를 먼저 결정한다.

**수용 기준:** 사용자가 “데이터가 오래된 것인지, 평점이 원래 없는지, 조회가 실패한 것인지”를 구분할 수 있다.

## P2 — 테스트 이후의 제한적 구조 개선

### P2-1. `App.tsx`를 조립 컴포넌트로 축소

한 번에 전면 재작성하지 않는다. 다음 순서로만 추출한다.

1. `place-query.ts`: 필터·정렬·번호 순서 계산 — 순수 함수와 테스트.
2. `useDataLoad`: places→ratings→google 합류와 상태 전이.
3. `useSearchState`: query, near, region, category, filter와 검색 실행.
4. `useUrlSync`: URL 읽기/쓰기와 popstate.

`App.tsx`는 지도, 목록, 상세에 props를 연결하는 역할을 남긴다. 기존의 원인 설명 주석은 관련 훅/함수로 함께 옮기며 삭제하지 않는다.

**중단 조건:** P0 테스트 없이 착수하지 않는다. 한 추출 단계에서 동작 diff가 생기면 다음 추출로 넘어가지 않는다.  
**수용 기준:** 기능·URL·모바일 실측이 동일하고, 추출한 각 경계가 독립 테스트된다. LOC 감소 자체는 완료 기준이 아니다.

### P2-2. `MapView.tsx`는 계산과 SDK 명령만 분리

최소안은 번호 마커 결정, 반경 줌, 선택 위치 계산 등 순수 계산을 별도 모듈로 옮기는 것이다. Kakao SDK의 명령형 객체 수명은 먼저 유지한다.

확장안인 `useKakaoMap/useMarkers/useSelection/useDiscoverLayer` 분리는 최소안 안정화와 지도 스모크 테스트 뒤에만 검토한다. 파일 전체의 `any`를 한 번에 없애려 하지 않고, 필요한 SDK 표면만 얇은 타입으로 감싼다.

**수용 기준:** 마커 수·클러스터·선택 라벨·현재 위치·주변 발견이 기존과 같고, 계산부는 SDK 없이 테스트된다.

### P2-3. props 묶음은 도메인 단위로만

`ListToolbar`의 많은 props를 무조건 Context 하나로 숨기지 않는다. 검색값/필터값/지도범위처럼 함께 변하는 값과 액션을 작은 타입으로 묶는다. 전역 Context는 실제 중간 전달이 2단계 이상 반복될 때만 도입한다.

## 9. 구현 전 결정할 사항

1. **범위:** A/B/C 중 선택. 권고는 **B**.
2. **Worker 배포:** `CLOUDFLARE_API_TOKEN`을 GitHub Secret에 두고 자동 배포할지, 수동 배포를 공식 절차로 유지할지. 토큰 설정 전에는 실행 불가능한 workflow를 만들지 않는다.
3. **동기화 이슈 #4:** 이번 범위에서 `NAVER_COOKIE` 갱신과 재실행까지 처리할지, 운영 별건으로 둘지. 데이터 신뢰 관점에서는 포함 권고.

5. **데이터 정보:** 별도 `meta.json` 추가를 허용할지. 허용하지 않으면 화면에는 개별 Google `at`과 현재 파일 수만 표시 가능하다.
6. **구글 정책 리스크 재검토 조건:** 현재 영구 보관 결정을 유지하되, 외부 공개 확대·상업화·다중 사용자 전환 시 재검토하는 조건을 명문화할지. 명문화 권고.
7. **P3 지도 잔여:** 이번에는 계속 유보할지. 권고는 유보 후 1주 실사용 피드백 수집.
8. **구조 부채 처리 수준:** 권고안 B는 `App.tsx`·`MapView.tsx`를 테스트 가능한 최소 경계까지만 나누며 전면 분해는 하지 않는다. 이번에 구조 부채를 크게 줄이는 것이 우선이면 C를 선택해야 하며, 그 대신 사용자 기능보다 리팩터 비중과 지도 회귀 위험이 커진다.

## 10. 구현 시 보고 방식

사용자가 과거 작업에서 실제 진행률과 완료 시점을 반복 확인한 점을 반영한다.

- 최종: 완료/유보/실패를 분리하고, “구현됨”과 “배포·라이브 확인됨”을 별도 표기.
