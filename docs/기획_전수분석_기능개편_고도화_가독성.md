## 0. 요약 (TL;DR)

맛핀은 "네이버 즐겨찾기 4,084곳을 지도·목록에서 보고 3사 평점을 카드 한 줄에서 비교"하는 앱이다. 제품 골격은 완성 단계이고, 최근 로그는 대부분 **회귀 수정과 UX 정합성 복구**였다(지도↔목록 연동, 모바일 시트 공간, 히스토리, 구글 값 보관).

전수 분석 결과 핵심 결론은 셋이다.

1. **제품 기능은 충분히 구현됐다.** 검색 라우팅, 반경/지도범위/전체 3-스코프, 3사 베이지안 통합 평점, 영업시간 요일 보정, URL 상태 복원, PWA, 온디맨드 Worker, CI 데이터 파이프라인까지 동작한다.
2. **가장 큰 구조 부채는 `App.tsx` 단일 컴포넌트(약 640줄, 상태 30+개)** 다. 모든 상태·effect·핸들러가 한 함수 안에 있어 결합도가 최고이고 테스트가 불가능하다.
3. **테스트 공백은 "규칙(순수 함수)"이 아니라 "상호작용(React/effect)"에 있다.** `selftest.mjs` 는 파싱·평점·URL 왕복·매칭을 잘 덮지만, 컴포넌트·effect·데이터 로딩 경로는 자동 검증이 0이다.

우선순위 후보(상세는 §7):
- **P0** `App.tsx` 상태 로직을 커스텀 훅으로 추출 → 테스트 가능 지점 확보
- **P0** 프런트엔드 테스트 러너 도입(effect·필터·정렬 회귀 방지)
- **P1** MapView의 명령형 Kakao 레이어를 훅으로 분리(마커/오버레이/선택/발견)
- **P1** 로딩·에러·빈 상태의 상태 머신화(현재 boolean 3~4개가 흩어져 있음)
- **P2** 접근성·가독성 잔여(정렬 select 네이티브, 색군 대비, 검색 결과 라이브리전)

## 2. 사용자 흐름 (실제 코드 기준)

```
진입
 └ readUrl() → initial (App.tsx:44)
    ├ places.json 로드 → 목록·지도 렌더 (dataState:'ready')
    ├ ratings.json 지연 로드 → 카드 평점 채움 (ratingsLoading)
    └ URL에 place=… 있으면 상세까지 복원

검색창 입력 (ListToolbar → App.runSearch)
 ├ parseQuery: "강남역 일식" → cat=[일식], text="강남역"
 ├ 지명꼴(역/공원/…) 또는 이름 미일치 → geocodePlace → near 중심점
 └ 가게 이름 일치 → textFilter (지도범위 안에서 좁힘)

목록 구성 (App.filtered)
 near 있으면 반경 / scope=all이면 전체 / 아니면 visiblePlaces
 → applyFilters(region·cat·text·unvisited·open·min) → sort

지도 조작
 마커 클릭 → onSelect → (모바일)시트 half + 상단 고정 / (데스크톱)상세 패널
 고른 카드 재클릭 → onDetail → 상세
 지도 이동 → handleViewChange → follow면 즉시 반영, 아니면 pendingView + "이 지역에서 다시 찾기"

상세 열기/닫기
 detailPlace 설정 시 writeUrl(push) → 뒤로가기로 목록 복귀 (App.tsx:384 pushedRef)
```

흐름 자체는 3사 벤치마크(네이버/구글 PC)에 맞춰 정합적이다. 문제는 **이 흐름 전체가 `App.tsx` 한 파일에 인라인**이라는 점(§3).

## 3. 구조적 병목 — 파일별 복잡도·결합도

### 3.1 `src/App.tsx` — 최우선 병목 (약 640줄)

측정 근거:
- `useState` 30개 이상(데이터 3 + 질의 12 + 지도 8 + 발견 4 + 껍데기 다수). `App.tsx:39`~`120` 구간.
- `useMemo`/`useCallback`/`useEffect` 합계 20개 이상. `filtered`(`App.tsx` 대형 useMemo)는 places·visiblePlaces·near·radius·scope·applyFilters·ratings·means·sort·origin 10개 의존.
- `applyFilters` 는 region·categories·textFilter·index·unvisitedOnly·visitedIds·openOnly·minScore·ratings·means·hasHours·hasScores 12개 의존.

결합도 문제:
- **모든 파생 상태가 렌더 함수 지역 변수**다. 한 곳도 독립적으로 테스트할 수 없다.
- URL 쓰기 effect(`App.tsx:365~385`)는 14개 값 배열에 의존한다. 하나만 놓쳐도 상태-URL 불일치가 조용히 생긴다(과거 `O5` 히스토리 버그가 정확히 이 부류였다 — 지도UX 문서 참고).
- effect 간 암묵 순서 의존이 주석으로만 보증된다("near가 deps에 있어서…", "centerForPopup을 deps에 넣지 않는다"). 주석이 곧 테스트를 대신하고 있다.

가독성 부채:
- 주석 밀도는 매우 높고 품질도 좋다(왜 그렇게 했는지 설명). **하지만 코드 자체가 길어 탐색 비용이 크다.** 새 기능을 넣으려면 640줄을 먼저 읽어야 한다.

### 3.2 `src/components/MapView.tsx` — 두 번째 병목 (약 620줄)

- `useRef` 15개 이상(kakao/map/images/markers/markerBySid/clusterer/circle/me/disc/prevSelected/appliedNumbers/numberImages/suppressClick/info/disc). `MapView.tsx` 상단 ref 블록.
- 명령형 Kakao SDK 제어와 React 렌더가 한 컴포넌트에 섞여 있다. effect 10개가 각각 마커·필터·번호·선택·오버레이·반경·발견을 담당.
- `createRoot` 재사용, `CustomOverlay` transform 트릭, `centerForPopup` 투영 좌표 계산 등 **SDK 내부 동작에 기댄 코드**가 다수. 하나가 깨지면 원인 추적이 어렵다(주석이 실측으로 방어).
- `/* eslint-disable @typescript-eslint/no-explicit-any */` 파일 전체 — 타입 안전성 없음(카카오 SDK가 `any`). 이는 SDK 한계라 불가피하나, 얇은 타입 래퍼(`kakao.ts`가 일부 담당)를 넓히면 완화 가능.

### 3.3 그 외 관찰

- `ListToolbar.tsx`(약 300줄)는 props 25개 이상. App의 상태를 그대로 통과시키는 **prop-drilling 허브**. App 훅 추출 시 함께 컨텍스트/훅으로 정리 대상.
- `worker/index.js`(약 400줄)는 단일 파일이지만 라우트·KV·쿼터·cron이 함수로 잘 분리돼 있어 상대적으로 건강하다. `overQuota` 비원자성은 주석에 명시되어 있고 Google Cloud 콘솔 쿼터로 이중 방어 — 설계 판단으로 수용.
- `src/lib/*` 는 대체로 순수 함수라 건강하다. `rating.ts`·`hours.ts`·`search.ts`·`url-state.ts` 는 이미 selftest가 덮는다.

**품질이 높다.** "틀려도 화면은 멀쩡한" 규칙을 정확히 겨냥했다.

로그에서 **같은 종류의 문제가 반복**된다:

1. **"상태가 화면·URL·히스토리와 어긋난다"** — `O5`(push가 replace로 샘), `120c34e`(선택 유실), `0e1d1c2`(지도 없을 때 0곳). → **상태 관리가 흩어져 있다는 신호.** §3.1·§7 P0의 직접 근거.
2. **"모바일에서 읽을 공간이 없다"** — 시트 108px→56px, 카드 40px 줄 제거, 칩바 시트 안으로. → 공간 예산이 빠듯. 이후 기능 추가 시 **공간 회귀 테스트**가 필요.
3. **"데이터 없음과 실패를 구분하라"** — `worker.ts` reject 정책, RatingRow "미매칭/별점없음/수집전", `hasHours` 게이트. → 이미 잘 지켜지는 원칙. 신규 기능도 이 원칙 유지가 요구됨.
4. **"무료 한도·약관 안에서 굴려라"** — 구글 값 보관, cron 대신 view-refresh, 월간 전량재수집 방지. → 비용/약관이 설계 제약. 신규 데이터 기능은 이 게이트를 먼저 통과해야 함.

### 5.3 로그가 드러낸 미완결 항목

- `useVisits.exportJson`(`visits.ts`) 구현됐으나 **어떤 컴포넌트도 호출하지 않음.** 방문기록 백업 UI 부재 → 브라우저 교체 시 기록 유실. (grep: `exportJson` 호출부 없음)
- 구글 3열은 코드·Worker·CI 다 있으나 기본 배포에서 **꺼져 있음**(`GOOGLE_ENABLED`). "구현했으나 미노출". 켜는 것은 게이트(verify) 통과 + `vars` 설정 문제.

## 6. 가독성 부채 (구체)

| 항목 | 위치 | 문제 | 개선 방향 |
|---|---|---|---|
| 거대 컴포넌트 | `App.tsx`(~640), `MapView.tsx`(~620) | 탐색·수정 비용 | 훅 추출(§7) |
| prop-drilling | `ListToolbar.tsx` props 25+ | 시그니처 비대 | 훅/컨텍스트로 묶기 |
| 정렬 컨트롤 불일치 | `ListToolbar.tsx` 네이티브 `<select>` | 나머지는 SEED. 스타일·a11y 불일치 | SEED 컴포넌트 or 세그먼트로 통일 |

## 7. 우선순위 후보

각 항목은 **근거 → 제안 → 검증 방법**으로 적는다. 코드 수정은 이 문서 범위 밖(구현 전 기획).

### P0-1. `App.tsx` 상태 로직을 커스텀 훅으로 추출
- 근거: §3.1(상태 30+·useMemo 20+), §5.2-1(상태 불일치 반복 버그).
- 제안: `useQueryState`(검색·필터·정렬), `useMapState`(center·level·follow·pending), `useDataLoad`(places·ratings·google), `useUrlSync`(readUrl/writeUrl 단일화)로 분리. 렌더 함수는 조립만.
- 검증: 추출된 훅에 대해 `applyFilters`·정렬·URL동기화 단위 테스트 추가(§P0-2 러너 사용). 리팩터 전후 화면 동작 동일성은 수동 스모크 + 스냅샷.

### P0-2. 프런트엔드 테스트 러너 도입
- 근거: §4.2 상호작용·상태 검증 0.
- 제안: Vitest + React Testing Library(Vite 프로젝트라 정합적). 대상: 필터/정렬 조합, 로딩 상태 전이, URL 왕복(기존 selftest와 중복은 흡수 or 유지).
- 검증: `npm test`에 프런트 테스트 편입, CI(`enrich.yml`/`deploy.yml`)의 `npm run test` 단계가 그대로 태움.

### P1-1. MapView의 명령형 Kakao 레이어 분리
- 근거: §3.2(ref 15+·effect 10·`any` 전면).
- 제안: `useKakaoMap`(초기화·bounds), `useMarkers`(생성·색·번호·클러스터), `useSelection`(선택 그림·오버레이·centerForPopup), `useDiscoverLayer`. 렌더 컴포넌트는 오버레이 컨텐츠만.
- 검증: SDK를 얇게 래핑해 목 가능하게. 최소한 `levelForRadius`·`centerForPopup` 계산부는 순수화해 단위 테스트.

### P1-2. 로딩/에러/빈 상태 상태머신화
- 근거: §4.2, `dataState`+`ratingsLoading`+MapView `status` 가 분산.
- 제안: 명시적 상태(`idle→loading→ready|error`, ratings 별도 트랙) 타입 1개로 통합. 화면 분기를 한 곳에서.
- 검증: 상태 전이 단위 테스트.

### P1-3. 방문기록 백업 UI 연결 + 가져오기
- 근거: §5.3(`exportJson` 미연결, 단방향 파이프라인이라 유실 위험 실재).
- 제안: 상세 "내 기록" 절 또는 헤더에 내보내기/가져오기. localStorage only 원칙 유지.
- 검증: export→import 왕복 단위 테스트.

### P2-1. 접근성·가독성 잔여
- 근거: §6.
- 제안: 정렬 컨트롤 SEED 통일, 검색 안내 `aria-live` 정합, 색군 대비 재측정(다크 포함).
- 검증: 자동 a11y 린트(예: eslint-plugin-jsx-a11y) + 수동 대비 측정.

### P2-2. 구글 3열 활성화 게이트 문서화·자동화
- 근거: §5.3(구현됐으나 미노출), `google-seed.yml` verify 게이트.
- 제안: 켜는 절차를 setup/README에서 한 곳으로. `/health` builtAt 확인을 CI 스텝으로.
- 검증: verify 오류율 ≤5% 확인 후 `vars` 세팅.

### 우선순위 근거 요약
- **P0는 "다음 기능·수정을 안전하게 만들기 위한 토대"** 다. 로그가 보여준 반복 회귀(§5.2-1)의 근본 원인이 상태 분산과 테스트 공백이므로, 여기에 먼저 투자하는 것이 이후 모든 작업의 비용을 낮춘다.
- P1은 두 번째 병목(MapView)과 상태 명료화.
- P2는 사용자 체감 개선 + 이미 만든 기능(구글 3열·백업) 마무리.

## 8. 하지 말아야 할 것 (안티 목표)

로그와 주석이 명시적으로 경계한 것들. 개편 시 재발 금지.

- 데이터 JSON을 precache에 넣지 않는다(`vite.config.ts` 주석: 2.7MB 이중 다운로드).
- 구글 rating을 공개 레포/빌드에 저장하지 않는다(약관, `worker.ts`·README).
- cron으로 전량 갱신하지 않는다(무료 한도, `enrich.yml`·`worker/index.js` `refreshOldest`).
- 실패를 "데이터 없음"으로 삼키지 않는다(`worker.ts`·RatingRow 주석).
- 지도 이동으로 목록 스크롤을 되감지 않는다(`PlaceList.tsx` `resetKey`·`listSignature`).
- "왜"를 설명하는 주석을 리팩터 중에 잃지 않는다(§6 주의).
